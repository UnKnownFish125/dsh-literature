**二、遗漏风险**
- **P0：发布权限与执行权限。** GitHub 直装和 agent 自审自发都可能把恶意指令或脚本带入运行环境。导入、审核、发布须分权；skill 内容不能授予工具权限，凭据和执行能力必须由宿主限制。“正文校验通过”也不能证明安全。
- **P0：全局传播导致数据泄露。** deepmemory 蒸馏可能包含项目路径、客户数据、凭据或内部流程。全局收录属于扩大可见范围，必须单独批准；usage≥3、7 天无修正不构成质量或脱敏证明。
- **P0（开放导入/发布前）：文件系统安全。** 禁止路径穿越、越界符号链接和利用 slug 覆盖任意路径；限制包大小、文件数，导入时不执行包内代码，不覆盖无归属记录的本地 skill。
- **P1：管理权与生效状态未定义。** 来源、管理、运行是三个维度，不是三态。literature 只能对“已接管的版本”成为权威；未受管文件、同名遮蔽、本地修改必须有明确处理规则。
- **P1：数据库与文件系统不一致。** 区分期望版本、磁盘已安装版本、实际被 DSH 选中的版本。失败可以不回滚库内内容，但必须标记发布失败，并具备幂等重试、校验、对账和回滚能力。
- **P1：统计及自动退役不可靠。** 同一任务可多次加载多个 skill；需去重、版本归因、未知结果和采集器身份。低评分只能触发复核，不能直接删除；只读文件若仍可被发现加载，就不算退役。
- **P2：质量与兼容性契约缺失。** 记录依赖、所需工具、DSH 兼容范围、许可证和测试样例。“不进 system prompt、不击穿缓存”也需要验证发现列表与上下文注入机制，不能仅由按需加载推出。

**三、推荐表结构**
七表不是天然过度工程，但一次全部实施没有必要。建议近期四表，自动部署时加第五表，自动统计时再加事件表：

| 表 | 核心字段 |
|---|---|
| `skills` | `id, scope, workspace_id, slug, title, description, category_id, lifecycle, created_at, updated_at, deleted_at` |
| `skill_versions` | `id, skill_id, revision, artifact_ref, content_sha256, manifest_json, source_type, source_url, source_ref, provenance_json, review_status, reviewed_by, reviewed_at, created_at` |
| `skill_feedback` | `id, version_id, kind, actor_id, value, rubric_version, evidence_ref, task_id, created_at`；kind 区分用户评分、agent 自评和任务结果 |
| `skill_audit` | `id, principal_id, action, target_type, target_id, request_id, details_json, created_at`；普通内容 API 不允许修改 |
| `skill_deployments`，后加 | `id, version_id, target_id, target_path, observed_hash, status, idempotency_key, error, deployed_at` |
| `skill_usage_events`，后加 | `id, event_key UNIQUE, version_id, target_id, session_id, task_id, call_id, event_type, outcome, producer_id, occurred_at` |

约束与取舍：
- scope 约束：全局必须 `workspace_id IS NULL`；工作区必须非空。分别建立全局 slug、工作区内 slug 的部分唯一索引，不能依赖含 NULL 的普通联合唯一约束。
- `artifact_ref` 指向持久化、不可变的完整包，保留原始 frontmatter 和附件；manifest 仅用于索引，不能据它重建原包。版本唯一约束为 `(skill_id, revision)`。
- 暂不建 `skill_files`、`skill_sources`；出现文件级权限/查询、多来源关系查询时再拆。统计从事件派生，计数器仅作缓存。
- 分类必须检查 scope 相容；发布仅接受已审核的固定版本及哈希，审核后修改必须产生新版本。数据库需版本化迁移，不能只靠 `CREATE TABLE IF NOT EXISTS`。

**四、一周路径**
目标明确为“可管理、可追溯、可审核、可导出”，不承诺自动部署闭环。
1. **第 1 天：** 定义 scope、受管边界和审核角色；消除假默认工作区；完成迁移与隔离测试。保留共享 token 时，服务只能按单一受信管理员边界使用，不能宣称具备多租户授权。
2. **第 2–3 天：** 四表、draft 导入、不可变整包版本、元数据查询、人工评分；验证未知 frontmatter、附件、路径穿越和同名冲突。
3. **第 4 天：** 实现版本审核和带哈希的整包导出；由管理员安装到实例专属目录，核对优先级及实际选中版本，保留上一版。
4. **第 5 天：** 跑完整回归、备份恢复和手工回滚；预留 deepmemory draft 接口，但不自动全局发布。自动使用统计及低效果退役延后，不填造计数。

**五、五项决策**
| 决策 | 建议 |
|---|---|
| 权威源 | **1A，但限于受管 skill。** 运行目录是部署副本；本地漂移只告警，显式导入后才成为新版本，不自动双向覆盖。 |
| 工作区 | **不选无条件 2A。** 支持 global/workspace，默认保留来源工作区；全局发布需批准。全局复用价值不等于可以绕过隔离。 |
| 评价口径 | 用户 1–5 星；agent 自评保留独立量表、模型和证据；任务结果独立记录。不合成一个“总分”，不默认每次加载都调用 LLM 评分。 |
| 部署方式 | **近期 4B，后续受控 4A。** 自动发布由独立、最小权限的发布器执行，literature 服务不直接获得所有运行目录写权限。 |
| 表结构 | **5A 独立领域模型，分阶段拆表。** 复用分类、认证、审计基础设施，不把 skill 的发布语义硬塞进 `knowledge_items`。 |

生命周期保留四态即可；版本审核状态、发布状态另外建模，不必把 review/staged 都塞进主生命周期。deepmemory 改为写 draft 是合理的安全闸口，但必须取消旧的直接写盘路径，并为重试设置幂等键，避免双写和重复蒸馏。

**六、架构替代**
最小方案就是“literature 管内容与评价，管理员审核整包后安装”。它牺牲即时更新，但显著缩小服务端权限，适合当前鉴权基础。

更长期可采用 **Git/制品仓库作为版本权威 + literature 管目录与评价 + 各实例发布器拉取已批准哈希**。适合多实例、代码审核和回滚要求较高的环境；代价是增加仓库与发布流程。一周内优先人工导出，不必同时建设这套基础设施。
